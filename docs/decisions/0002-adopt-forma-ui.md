# 0002 · Adopt Forma UI for components and tokens

Status: accepted (2026-10-13, owner)

## Context

Draftroom needs buttons, fields, dialogs, tabs, tooltips, icons, light and dark themes and a shared set of design tokens. [Forma UI](https://github.com/Yelison/forma-ui) is a component library and token set maintained alongside Draftroom; it is MIT-licensed, ESM, has no runtime dependencies and peers on React 19. Draftroom should consume it as any other application would, without bending it.

Forma UI 0.3.0 provides `Button`, `IconButton`, `Icon`, `Badge`, `Field`, `Input`, `Radio`, `Tabs`, `Tooltip` and `Dialog`/`Modal`; a theme store (`createThemeStore`, `useTheme`, `themeScript`) that switches light, dark and system through a `data-theme` attribute on `<html>`; and `tokens.css` with colour, typography, spacing, radius, control-size, motion and z-index tokens. It does not provide an avatar, a menu or popover, a select or listbox, a toast, a checkbox or switch, a skeleton or table styles.

## Decision

- **Exact version.** `@yelison/forma-ui` is pinned to exactly `0.3.0`, with no range. Moving to another version is a pull request of its own.
- **Components come from Forma UI.** Draftroom imports them from `@yelison/forma-ui`. Its two internal strings (`buttonLoading` and `dialogClose`) are passed through `FormaProvider`, so they are translated with the rest of the interface (ADR 0003). The stylesheets load in the order Forma UI documents, `base.css` and `styles.css` first.
- **Themes use Forma UI's theme store.** Theme switching and the inline head script come from `createThemeStore` and `themeScript`; Draftroom does not write its own.
- **Forma UI's tokens are a synchronised copy.** `apps/web/src/styles/forma-tokens.css` is a byte-for-byte copy of the package's `tokens.css`, regenerated by `npm run sync:forma-tokens`. A test fails if the copy differs from the installed package, so an upgrade that changes a token shows up as a diff in the pull request that makes it.
- **Product tokens live apart.** Tokens that only Draftroom needs, such as editor typography, layout widths and presence colours, are in `apps/web/src/styles/draftroom-tokens.css`, a generated file whose header names its generator. A test fails if that file redeclares any Forma UI token.
- **Never redefine a Forma UI token.** When a product value differs from a Forma UI token, Forma UI's value is adopted; if it is genuinely wrong, a change is requested from Forma UI. It is never overridden locally.
- **Missing generic pieces are requested from Forma UI.** The gaps listed above are asked of Forma UI. Until they arrive, Draftroom builds the ones it needs, such as an avatar, in its own `components` folder, shaped so they can be swapped for Forma UI's. Draftroom-specific components (presence, sync status, document row, comment card, permission) stay in Draftroom.
- **Styling.** CSS Modules, flat, using tokens only: no literal colours, spacing or sizes, and no `!important`.

## Consequences

- Draftroom looks and behaves like the other applications built on Forma UI, and exercises the library in a real one.
- A pinned version means no surprise from a patch release; the price is a deliberate upgrade each time.
- Keeping a copy of the tokens duplicates a file, but it makes token changes reviewable and keeps the app's stylesheet order in one place.
- Needing something Forma UI lacks can wait on another project. The in-Draftroom stand-ins add a little code that is later deleted.
- Two token files means two sources to read; the separation test is what keeps them from overlapping.

## Alternatives considered

- **Build Draftroom's own component and token set:** more control, and a duplicate of a library the owner already maintains.
- **Another component library** such as Radix or MUI: capable, but each brings its own token system alongside the one Draftroom already has.
- **Import `tokens.css` straight from the package** instead of copying it: no duplicate file, but token changes would arrive silently with a version bump instead of as a reviewed diff.
- **A caret range on the Forma UI version:** convenient, and it would let a minor release change tokens or components without a pull request.
- **Override a Forma UI token where the product needs a different value:** quick, and it splits the meaning of the token between the two projects.

## Amendments

- 2026-10-13: Forma UI moves to exactly `0.4.0`, superseding the `0.3.0` pin above. Draftroom adopts its `clock` icon (replacing the one drawn in the app) and the regenerated token copy; the new Avatar, SearchField, hidden-label Input and native Select, and the other new icons and tokens, stay available for the screens that need them. The avatar and the select are therefore no longer among the gaps listed in the context: screens use Forma UI's instead of building their own, as the "Missing generic pieces" decision above would otherwise suggest.
- 2026-10-13: Forma UI moves to exactly `0.5.0`. It brings the purple tokens, Badge `tone="purple"` and `shape="pill"`, `FilterChip`, `Button size="compact"`, `initialsOf` and the `@layer base` rule for resets; for now only the purple is adopted, through its tokens (the product's provisional pair is gone, ADR 0008), and the rest stays available for the screens that need it.
