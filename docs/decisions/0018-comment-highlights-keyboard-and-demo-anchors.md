# 0018 · Comment highlights, the key that comments, and the starting text of the demo

Status: accepted (2026-10-17, T3.2)

## Context

T3.2 shows the threads of a document as highlights in the text and lets a person comment from a selection, with the mouse or the keyboard, whatever the editor allows them to change. Three choices were not obvious and each had a failure that the tests found or the review reproduced:

- **Where the highlight of a thread is.** A thread is anchored with two Yjs relative positions (protocol §10), so Yjs says where it is. The editor, though, applies the person's own typing before the sync plugin writes it into Yjs (the binding writes in the `update` of its view, after the transaction), so the Yjs document is behind the editor for exactly the person who is typing. ProseMirror can map a range through that typing at once, but its `StepMap` ignores the association of an end when the end meets the edge of a replaced range: typing over the commented text left the highlight (and the card, which reads the same state) on the new text for the person who typed, while everyone else saw an orphan. Typing where a range that starts at the end of a paragraph begins (§10.2, the accepted fallback) left the typed text out for the person who typed and in for the others.
- **The key that comments.** A commenter's text is not editable (`editable` is false), and ProseMirror runs `handleKeyDown`, where Tiptap puts every shortcut, only for an editable view: `keydown` is one of its `editHandlers`. A shortcut registered the usual way does nothing for a commenter, who must be able to comment.
- **The starting text of the demo.** The demo has no server: the mock writes the starting text of a document into the live Yjs document when it is first opened, and the threads of the fixtures are anchored in that text. An anchor names Yjs items by client and clock. Text written from JSON gets a new random client every time, so the anchors of the fixtures would point at nothing in the next tab or the next reload, and two tabs that each wrote the text would have written it twice.

## Decision

1. **Yjs is the source of the final state of a highlight and of a card.** The plugin keeps the editor's own mapping as the first drawing of the person's own typing, so the highlight does not lag a keystroke. In the next microtask after a transaction of the person that changed the document, when the sync plugin has written it into Yjs, the plugin reads every thread from Yjs again (a transaction with a meta of its own). Changes of other people, undo, and a change of the threads read from Yjs as before. The highlight, the state of the card (`open` or `orphaned`) and the range the key and the click use are therefore always what Yjs says, for the person who types and for everyone else. The microtask does not depend on the order of the views: it runs after the whole `dispatch`. What depends on the order of the plugins is the `apply` of the highlight plugin, which reads the state of the sync plugin from the new editor state (`isChangeOrigin`, and the document to resolve in): that field exists only if the sync plugin comes first, which the higher priority of the collaboration extension gives. A highlight extension put before it breaks most of the tests of the plugin (30 of 36 in the review's mutation).
2. **The key is a `keydown` handler of the DOM (`handleDOMEvents`), which runs for every role, and the handler cancels the event.** It uses the `keydownHandler` of `prosemirror-keymap`, so the name of the key (`Mod-Alt-m`), the label on the button (`shortcuts.ts`) and the platform rules (Command on a Mac; on Windows, where AltGr arrives as `Ctrl+Alt`, the key code is not used as a fallback, so `AltGr+M`, which types a character on some layouts, is not taken for the shortcut, while `Ctrl+Alt+M` works as it is written) come from the same notation as the other shortcuts. ProseMirror cancels the event of a key that `handleKeyDown` took and does not for one taken here, so the handler calls `preventDefault()`: on a Mac the browser would otherwise go on to do what it does with Option+Command+M. With text selected the key starts a comment; with the caret in a highlight, or touching its end, it takes the person to the thread; `Esc` in a card takes them back to the text.
3. **The mock writes the starting text of the demo as a fixed Yjs client chosen by the language, the document and the content.** The client id is a 32-bit FNV-1a hash of `<language>:<document>:<JSON of the content>`. The same text gives the same items in every tab, reload and build, so the anchors of the fixtures resolve and two tabs that both write the text write the same items, which Yjs merges into one. The language and the document are in the name because two texts must not share items: a copy that a browser kept in IndexedDB of the English text, opened in Spanish, would otherwise be taken for the same items and the two sides would disagree about the text. The content is in the name for the same reason across builds: a later build that edits `demoContent.ts` must be another client, which is what the demo had before this decision (the old and the new text then meet in the document, as a stale copy always did), and not a collision. Anchors are indexed as Yjs indexes, in UTF-16 units of the text without the tags of its formatting.

## Consequences

- A person who types over a commented text sees the card become an orphan at once, as everyone else does. Between the transaction and the microtask the highlight shows the editor's mapping; no frame of the browser paints in between, since a microtask runs before rendering.
- The cost of the second reading is the resolution of the open threads once for each transaction of the person, which is the cost the highlights already had for each transaction of someone else.
- The key of a commenter works, and does not leak to the browser. A page that wants another shortcut for the same job changes `commentShortcut`; the label, the `aria-keyshortcuts` and the hint follow.
- Editing the starting text of the demo is free of consequences for visitors who return: they get a new client and the text of the new build, possibly next to the old text, never a text that two sides read differently. Nothing of this reaches the real build: the modules are imported only from `data/mock`.
- The fixtures of the tests are not touched: their documents start empty, and the threads of the launch plan are orphans there, which the panel tests use.

## Alternatives considered

- **Keep the editor's mapping and fix its edge cases.** Rejected: a second implementation of the resolution of an anchor, in a place that does not see the deleted items Yjs resolves through, would always have a case in which it disagrees. Reading Yjs again is one rule.
- **Resolve from Yjs inside `apply` for the person's own typing.** Rejected: Yjs is not written yet there; it is the case this decision is about.
- **Dispatch the second reading from the `update` of the plugin's view.** Rejected: a view cannot take a transaction while it is being updated, so the dispatch waits for the end of that update anyway, and a microtask says so.
- **`Y.Doc` `afterTransaction` with the origin of the binding.** Possible, and independent of the order of plugins, but the origin of the binding is an implementation detail of `@tiptap/y-tiptap`, and the event also fires for the changes of other people, which already redraw the highlights.
- **Register the key with Tiptap and make the text of a commenter editable but inert.** Rejected: it changes what the text is for the browser (a caret, a keyboard on a phone, an editing context for a screen reader) in order to receive a key.
- **One fixed client for the whole demo.** Rejected: two languages, or two builds, would share items that differ.
- **A random client and a table of anchors that is rebuilt on every open.** Rejected: the threads of the fixtures belong to the REST world of each tab and cannot know which client wrote the text in another tab.

## Update (0020, 2026-10-20)

The threads are now shown in the margin of the sheet and not in a panel ([0020](0020-comments-in-the-margin-one-scroll.md)). The keyboard flow of this decision is unchanged, and the thread that the key takes the person to is the active one of the margin. The highlight plugin also places the resolved threads without drawing them, so that their cards can be level with their text; the key and the click still reach only the open ones.
